# 새 팀 협업 절차와 영우 담당 범위

작성일: 2026-10-23. 4조 새 저장소 공지를 반영했습니다. 전달받은 저장소·브랜치 안내, 영우 역할 안내와 마지막 DM의 협업 절차를 정리한 문서입니다. 아래 체크리스트는 작업 계획이며 구현 완료를 뜻하지 않습니다.

## 이번 과제의 기준

- 저장소: https://github.com/KANT-2/group_4_vegetable_project
- 팀원: 지나, 서현, 영우, 형준
- 목표: 기존 못난이마켓 화면과 FastAPI를 연결합니다.
- 기존 README의 팀원·Next.js 서버 전용 설명·배포 주소는 이전 프로젝트 이력입니다. 새 FastAPI 서버 구현·배포 완료의 근거로 사용하지 않습니다.
- 다른 팀원의 기능별 역할은 전달받지 않았으므로 이 문서에서 임의로 배정하지 않습니다.

## 브랜치와 승인 흐름

**개인 브랜치 → PR·승인 → develop → 통합 검증 → PR·승인 → main**

| 단계 | 해야 할 일 | 다음 단계 조건 |
| --- | --- | --- |
| 개인 작업 | 최신 develop에서 개인 브랜치를 만들고 담당 기능 구현·검증 | 변경 범위와 검증 결과를 PR에 기록 |
| 1차 PR | 개인 브랜치에서 develop을 대상으로 PR 생성 | 다른 팀원 1명 이상 승인 후 머지 |
| 통합 검증 | develop에서 인증·상품·구매 흐름을 함께 검증 | 통합 검증 결과 기록, 발견된 문제 수정 |
| 2차 PR | develop에서 main을 대상으로 PR 생성 | 통합 검증 결과를 확인하고 다른 팀원 1명 이상 승인 후 머지 |

main·develop에는 직접 푸시하지 않습니다. 개인 브랜치를 main으로 직접 머지하거나, 승인 없이 자동 머지하지 않습니다. 이 문서는 협업 규칙을 기록한 것이며 GitHub 브랜치 보호 설정을 적용했다는 뜻은 아닙니다. 승인 요구를 시스템으로 강제하려면 저장소 관리자가 develop·main의 보호 규칙을 별도로 설정해야 합니다.

### 처음 저장소 받기

```bash
git clone https://github.com/KANT-2/group_4_vegetable_project.git
cd group_4_vegetable_project
code .
```

이미 내려받았다면 해당 저장소에서 진행합니다. 미커밋 변경이 있으면 먼저 보존하고 브랜치를 전환합니다.

```bash
git fetch origin
git switch develop
git pull --ff-only origin develop
```

본인 명령만 실행합니다. 이미 개인 브랜치가 있다면 새로 만들지 않고 해당 브랜치로 전환합니다.

| 이름 | 처음 개인 브랜치 생성 |
| --- | --- |
| 지나 | `git switch -c jina` |
| 서현 | `git switch -c seohyun` |
| 영우 | `git switch -c youngwoo` |
| 형준 | `git switch -c hyungjune` |

영우의 변경은 필요한 파일만 커밋하고 다음과 같이 올립니다.

```bash
git push -u origin youngwoo
```

형준의 `hyungjune` 브랜치는 이미 생성되어 있습니다. 영우는 `youngwoo`만 생성·푸시합니다. 푸시 권한 오류가 나면 팀에 알립니다.

GitHub에서 base를 `develop`, compare를 `youngwoo`로 선택해 PR을 만듭니다. 제목·본문에는 구현한 기능, 제외한 범위, 검증 결과와 남은 문제를 기록합니다. 통합 검증 후 만드는 배포 PR은 base `main`, compare `develop`입니다.

## 영우 — 장바구니·주문·모의 결제

서로 이어지는 구매 흐름에 집중합니다. 별도의 신규 운영 기능은 이번 필수 범위에 추가하지 않습니다.

- [ ] 장바구니 담기·조회·수량 변경·삭제
- [ ] 서버 기준 상품 금액·배송비 계산
- [ ] 주문 생성과 주문 당시 상품·가격·배송지 저장
- [ ] 내 주문 목록·상세 조회
- [ ] 기존 장바구니·결제·주문 화면과 FastAPI 연결
- [ ] 주문 생성과 장바구니 정리를 하나의 트랜잭션으로 처리

### 도메인 규칙

- [ ] 수량 범위를 검증합니다. 구체적인 허용 범위는 API 계약에 명시합니다.
- [ ] 빈 장바구니와 판매 중지 상품의 주문을 거부합니다.
- [ ] 클라이언트가 보낸 금액을 신뢰하지 않고 서버의 상품 정보와 배송 규칙으로 계산합니다.
- [ ] 동일 주문 요청의 중복 생성을 방지합니다.
- [ ] 로그인한 사용자는 본인 장바구니·주문만 접근할 수 있습니다.
- [ ] 주문 생성 중 실패하면 주문·주문 상품·장바구니 정리 중 일부만 반영되지 않도록 롤백합니다.

수량 상한, 배송비 정책, 판매 가능 여부의 판별 필드, 인증 전달 방식, 중복 방지 방식은 실제 API·DB 계약을 확인한 뒤 구현 문서에 기록합니다. 이전 프로젝트 값을 새 과제 규칙으로 임의 확정하지 않습니다.

### 완료 시연과 검증

1. 로그인 후 상품을 장바구니에 담습니다.
2. 수량을 변경하고 서버 계산 금액을 확인합니다.
3. 모의 주문을 생성합니다.
4. DB에 저장된 주문을 목록·상세 API로 다시 조회하고 주문 당시 상품·가격·배송지를 확인합니다.
5. 주문 생성 과정에 실패 상황을 만들어 일부 데이터만 저장되거나 장바구니만 비워지지 않는지 확인합니다.
6. 빈 장바구니·판매 중지 상품·잘못된 수량의 주문 거부를 확인합니다.
7. 같은 주문 요청을 반복해 중복 주문이 생기지 않는지 확인합니다.
8. 다른 사용자의 장바구니·주문에 접근할 수 없는지 확인합니다.

쿠폰 할인, 환불 승인, 실제 PG, 배송 추적은 이번 담당 필수 범위에 넣지 않습니다. 모의 결제 완료를 실제 결제 승인으로 기록하지 않습니다.

## PR에 남길 검증 기록

| 항목 | 기록할 내용 |
| --- | --- |
| 변경 범위 | 이번 PR에서 구현·수정한 기능과 관련 화면/API |
| 데이터 처리 | 서버 계산, 소유권 확인, 트랜잭션, 중복 방지 검증 |
| 실행 결과 | 실제 실행한 명령과 성공·실패 결과. 미실행은 미실행으로 표시 |
| 시연 | 구매 흐름 시연 결과와 실패 시 롤백 확인 결과 |
| 통합 | develop 통합 검증 결과 또는 검증 전임을 표시 |
| 남은 일 | 미구현·제약·후속 작업 |

문서만 수정한 PR은 기능 테스트를 통과했다고 적지 않습니다. 이번 문서 등록으로 장바구니·주문·FastAPI 연결이 완료된 것은 아닙니다.
