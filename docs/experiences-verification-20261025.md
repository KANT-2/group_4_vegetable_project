# 체험 예약 담당 Use Case — 구현·검증 기록 (형준)

작성: 2026-10-25. README·Notion·발표자료에 옮겨 쓸 초안입니다. **실제로 실행해 확인한 것과 아직 못 한 것을 구분해서** 적었습니다. 실제 인증(JWT 블랙리스트) 연동 결과는 이 문서에 없습니다(미완료).

## 1. 담당 Use Case

체험 목록·상세 조회 → 회차 선택 → 예약 → 내 예약 확인 → 취소, 관리자의 회차별 예약 조회·접수 마감.
체험·회차는 시드로 준비했고, 실제 참가비 결제·사진 업로드·체험 등록은 범위에서 제외했습니다.

## 2. 구조와 요청 흐름

`presentation(router·schemas·errors)` → `application(service·ports·read_models)` → `domain(models)` ← `infrastructure(models·repositories)`

- 도메인(`domain/experiences/models.py`): 표준 라이브러리만 사용. FastAPI·SQLAlchemy·Pydantic import 없음(검색으로 확인).
- 응용 서비스: 조회 → 도메인 메서드 → 저장 → commit, 실패 시 rollback. 같은 회차의 동시 예약은 회차 행 `FOR UPDATE` 잠금으로 순서대로 처리.
- Repository: ORM 모델 ↔ 도메인 객체 변환, 화면용 조회는 `ReservationDetail`(응용 계층 조회 모델).
- DB: PostgreSQL(새 Supabase) + SQLAlchemy 비동기 + asyncpg. 같은 사용자·회차의 활성 예약 중복은 부분 유니크 인덱스가 최종 방어.

## 3. 업무 규칙과 응답

| 규칙                                               | 위반 시 응답 |
| -------------------------------------------------- | ------------ |
| 참가 인원 1~10명                                   | 422          |
| 정원 초과                                          | 409          |
| 접수 마감 회차                                     | 409          |
| 시작했거나 지난 회차                               | 409          |
| 같은 회차 활성 예약 중복 (취소 후에는 재예약 가능) | 409          |
| 본인 예약만 취소                                   | 403          |
| 이미 취소된 예약 재취소 / 시작 24시간 이내 취소    | 409          |
| 없는 체험·회차·예약, 체험과 회차가 맞지 않음       | 404          |
| 관리자 API(예약 목록·접수 마감)에 일반 사용자      | 403          |
| 토큰 없음·위조·만료                                | 401          |

취소 기한 24시간과 최대 인원 10명은 팀 합의 전의 가정값입니다.

## 5. 실제 인증 연동과 화면 확인 (2026-10-26, 지나의 인증 PR #9 반영)

체험 API는 지나의 공통 인증(`app.presentation.accounts.dependencies`: `CurrentUser`·`AdminUser`)을 그대로 씁니다. 개발용 임시 로그인(`dev_login.py`, `DevLoginBar`)과 임시 어댑터는 제거했습니다(PR #12).

- 선행: 지나의 `app_users`·`revoked_tokens` 마이그레이션(`supabase/migrations/202610260001_accounts.sql`)을 새 DB에 적용(기존 테이블 변경 없음).
- `experience_reservations.user_id`는 `app_users(id)`를 외래키로 참조합니다(`202610260002_experience_reservation_user_fk.sql`, 삭제 시 cascade). 다른 기능의 테이블 외래키는 바꾸지 않았습니다. 중복 예약(부분 유니크 인덱스) 위반만 "중복"으로 알리고, 존재하지 않는 사용자 같은 다른 무결성 오류는 그대로 드러납니다.
- 프론트: 사이트 로그인(`/login`)이 쿠키(httpOnly)에 넣는 FastAPI 토큰을 서버가 읽어 호출합니다. 목록·상세는 서버 컴포넌트, 예약·취소·마감은 서버 액션(`src/actions/experiences.ts`). 로그인하지 않았거나 토큰이 무효하면 `/login?next=…`로 보내고 로그인 뒤 원래 화면으로 돌아옵니다.

## 6. 예외·경계값 점검 (2026-10-26)

실제 서버·DB에 이상한 입력을 보내 500 오류나 정보 누출이 있는지 탐색했습니다(임시 스크립트, 약 90개 요청). 시험 데이터는 끝나면 삭제했습니다.

- **점검 범위**: 목록 쿼리(음수·0·정수 오버플로·소수·SQL 문자·퍼센트·이모지·긴 문자열·널 문자), 경로 변수(잘못된 UUID·널 문자·경로 탈출), 인증 헤더 변형(없음·Bearer만·Basic·토큰 중복·alg=none), 예약 본문 변형 19종(null·문자열·소수·불리언·배열·객체·음수·거대 정수·무한대·깨진 JSON·폼 형식 등), 허용되지 않는 메서드, 시간 경계(시작한 회차·24시간 취소 기한 직전), 관리자 API 입력, CORS, 동시성.
- **찾은 문제 4건 (모두 500, 수정 완료)**: 목록 `page`에 아주 큰 정수, 검색어·지역에 널 문자, 체험 id에 `%00`, 인원에 `1e999`(무한대).
  - 수정: `page` 상한(최대 10,000)과 검색어 길이 제한, 널 문자 입력 422, 인원은 정수만 허용(`"2"`·`true`는 422), 입력 검증 오류 응답에서 사용자가 보낸 값(`input`)을 제거(무한대 처리 및 비밀번호 같은 값이 응답에 되돌아가지 않게 함), 처리되지 않은 오류는 스택 트레이스·SQL 없이 `{"detail": …}` JSON으로 응답.
- **동시성(정상 확인)**: 같은 사용자의 동시 10건 → 성공 1건·나머지 409, 서로 다른 7명이 1석에 동시 예약 → 성공 1건, 같은 예약 동시 취소 6건 → 성공 1건·잔여 인원 정확.
- **정상 확인**: 사용자 ID 위조(본문에 `user_id`를 넣어도 토큰 사용자로 저장), 시작한 회차·마감 회차 409, 취소 기한 24시간 규칙, 허용되지 않은 출처의 CORS 거부, 응답에 내부 정보 누출 없음.
- **팀원 API도 읽기 위주로 점검**(코드 변경 없음): 지나의 로그인 이메일, 영우의 장바구니 상품 id·경로 id에서 같은 종류의 500(널 문자)이 있었습니다. 각 기능의 파일을 고치지 않고 공통 오류 처리(`app/core/error_handlers.py`)에서 PostgreSQL 데이터 예외(SQLSTATE 22xxx)를 422로 바꿔 한꺼번에 막았고, 재점검에서 해당 4건이 모두 422로 바뀐 것을 확인했습니다.
- 회귀 테스트: `tests/test_experiences_api.py`(5건), `tests/test_foundation.py`(1건), `tests/test_common_error_handling.py`(3건). 백엔드 `pytest` 261건 통과.

## 7. 아직 못 한 것 · 알려진 제약

- **`/accounts/me`와 헤더·로그인 화면이 프로필 없는 계정에서 오류**: 지나의 `/me`는 프로필 행이 있어야 응답하는데, 개발 계정(`dev-user`·`dev-admin`)이 `app_users`에만 있고 `auth.users`·`profiles` 행이 없습니다(`profiles.id`는 `auth.users`를 참조). 그래서 개발 계정으로 로그인하면 헤더의 `/api/navigation`이 503이고, 로그인된 상태로 `/login`에 들어가면 오류 화면이 납니다. 체험 화면은 `/me`에 의존하지 않도록 토큰의 role로 화면만 구성하고 권한 검사는 API가 합니다. **합의된 해결 방향(지나 안 A')**: 사용자 생성 시 `auth.users`·`app_users`·`profiles`를 같은 UUID로 한 트랜잭션에서 만들고, 다른 기능 테이블의 외래키는 바꾸지 않습니다. 새 DB에서 이 생성이 가능한 것은 시험(롤백)으로 확인했고, 실제 절차 구현·검증은 지나 몫입니다.
- 화면의 role 표시는 토큰 값을 읽은 화면 구성용이라, 계정이 비활성화되어도 쿠키 토큰이 만료되기 전까지 관리자 메뉴가 보일 수 있습니다. 실제 접근은 API가 401/403으로 막습니다.
- 구매(장바구니) 모듈은 아직 옛 임시 인증에 의존해서 `main.py`에 등록하지 않았습니다. 영우가 인증을 지나 모듈로 바꾸고 테스트를 고친 뒤 등록하고, 호환용 어댑터를 삭제합니다.
- 화면에서 로그아웃 버튼을 눌러 확인하지는 못했습니다(위 `/me` 문제로 헤더 메뉴가 안 나옴). 로그아웃 차단은 API 수준으로 확인했습니다.
- 개발용 계정 2개(`dev-user@example.test`, `dev-admin@example.test`)가 새 DB에 있습니다. 비밀번호는 `backend/.env.dev-accounts.local`(Git 제외)에만 있습니다.
- 취소 기한 24시간·최대 10명은 팀 합의 전의 가정값입니다.
