## 비회원 장바구니 합치기 API (멱등)

`POST /api/v1/purchases/cart/merge` — 요청: `{"items": [{"product_id", "quantity"}, ...]}` (1~50줄), 응답 200: `{"merged": 2, "skipped_product_ids": [...]}`.

| 상황                                                                | 상태                                            |
| ------------------------------------------------------------------- | ----------------------------------------------- |
| 토큰 없음·로그아웃                                                  | 401                                             |
| 줄이 없거나 51줄 이상, 수량이 1~99가 아님, `user_id` 같은 다른 필드 | 422 (아무것도 저장하지 않음)                    |
| 판매가 끝났거나 없는 상품                                           | 그 상품만 건너뛰고 `skipped_product_ids`로 알림 |

**합치기는 멱등입니다.** 수량을 더하지 않고 `max(기존 수량, 비회원 수량)`으로 맞춥니다(SQL `GREATEST`, 한 문장이라 동시에 실행돼도 같은 결과). 그래서 서버는 반영했는데 응답만 유실돼 같은 요청을 다시 보내거나(새로고침) 두 탭에서 동시에 보내도 수량이 두 번 더해지지 않습니다. 새 테이블이나 멱등 키 저장이 필요 없습니다. 상품은 상품 ID 순서로 처리하고 한 트랜잭션이라 중간에 실패하면 아무것도 반영되지 않습니다.

- 계정 장바구니에 당근 3개, 비회원 장바구니에 당근 2개가 있으면 3개가 됩니다(5개가 아님). 같은 상품이 양쪽에 있을 때 합산하지 않는 대신 재시도 안전성을 얻었습니다. 합산이 필요하면 별도 멱등 키 저장소가 필요합니다(팀 확인 필요).
- 프런트는 성공 응답을 받았을 때만 쿠키를 지웁니다. 서버 장애·연결 끊김이면 쿠키를 남겨 다시 시도하고(안전), 요청이 거부되면(4xx) 다시 보내도 성공할 수 없어 쿠키를 지우고 합치지 못했다고 알립니다.
- 리뷰(지나 님) 지적: "서버는 성공했는데 응답만 실패하면 재시도에서 수량이 중복될 수 있다"에 대한 수정입니다. 옛 방식(상품마다 "수량 더하기"를 반복 호출)으로 되돌리면 새 DB 테스트 3개가 실패합니다.

## 주문 API

모두 `Authorization: Bearer <access_token>`이 필요합니다.

| 메서드·경로                            | 설명                                                                     | 성공               |
| -------------------------------------- | ------------------------------------------------------------------------ | ------------------ |
| `POST /purchases/orders`               | 모의 결제 주문 생성. 같은 `request_key`로 다시 요청하면 기존 주문을 반환 | 201 (재요청은 200) |
| `GET /purchases/orders?page=1&size=20` | 내 주문 목록(최신순, `{items,total,page,size}`)                          | 200                |
| `GET /purchases/orders/{order_id}`     | 내 주문 상세. 남의 주문·없는 주문은 같은 404                             | 200                |

요청 본문: `request_key`(UUID), `shipping`(받는 분·연락처·우편번호·주소·상세주소), `payment_method`(`card`/`bank_transfer`/`easy_pay`), 선택 `expected_total_amount`. `user_id`·금액 같은 다른 필드는 422로 거부합니다.

| 상황                                                                                                                                | 상태 |
| ----------------------------------------------------------------------------------------------------------------------------------- | ---- |
| 토큰 없음·로그아웃·비활성 계정                                                                                                      | 401  |
| 배송지·결제 수단·요청 형식 오류                                                                                                     | 422  |
| 빈 장바구니, 판매 중지·품절·재고 부족 상품, 화면 금액이 서버 계산과 다름 (재고 부족은 `available`=살 수 있는 최대 수량을 함께 응답) | 409  |
| 없는 주문·남의 주문                                                                                                                 | 404  |

### 환불 신청 접수

`POST /purchases/orders/{order_id}/refund` — 요청 `{"reason": "10~500자"}`. 환불 신청 표(`public.refund_requests`, 주문당 1건)에 접수만 합니다.

| 상황                                                   | 상태                                                         |
| ------------------------------------------------------ | ------------------------------------------------------------ |
| 처음 신청                                              | 201 `{status: "requested", reason, created_at, reviewed_at}` |
| 이미 신청한 주문에 다시 신청                           | 200, **처음 신청을 그대로** 반환(사유는 바뀌지 않음)         |
| 토큰 없음·로그아웃                                     | 401                                                          |
| 사유가 10자 미만·500자 초과, 모르는 필드(`user_id` 등) | 422 (저장 안 함)                                             |
| 남의 주문·없는 주문                                    | 404 (같은 응답)                                              |
| 결제 완료가 아닌 주문                                  | 409                                                          |

- 같은 사용자의 요청은 사용자 잠금으로 한 줄로 세우고, 저장은 `ON CONFLICT DO NOTHING` 이라 동시에 두 번 눌러도 한 건만 생깁니다.
- 주문 목록·상세 응답에 `refund` 가 추가됩니다(없으면 `null`). `GET /purchases/orders?refunds_only=true` 는 환불을 신청했거나 취소된 주문만 돌려줍니다(마이페이지 "취소·환불 내역").
- 화면: 주문 상세의 "환불 신청" → 사유 입력 → 접수 → 같은 화면에 접수 상태·접수일·사유 표시.

### 처리 방식

1. 사용자별 잠금(`pg_advisory_xact_lock`)으로 같은 사용자의 주문 요청을 한 줄로 세웁니다.
2. 같은 `request_key`의 주문이 이미 있으면 새로 만들지 않고 그 주문을 돌려줍니다.
3. 장바구니와 상품을 모두 쓰기 잠금(`for update of c, p`)으로 읽고, 판매 중·품절 아님·수량 ≤ 재고를 확인한 뒤 서버가 `products.price × 수량` + 배송비로 금액을 계산합니다. 상품 행도 잠가서 마지막 재고를 동시에 주문해도 한 명만 성공합니다.
4. 주문과 주문 상품(상품명·단위·단가·배송지 복사본)을 저장하고, 주문한 수량만큼 재고를 줄이고(`stock >= 수량` 조건부 차감), **주문한 상품만** 장바구니에서 지웁니다. 같은 `request_key`로 다시 요청하면 재고를 또 줄이지 않습니다.
5. 1~4는 한 트랜잭션입니다. 중간에 실패하면 전부 취소되어 주문만 생기거나 장바구니만 비워지지 않습니다.

`expected_total_amount`는 화면에 보인 금액입니다. 서버 계산과 다르면(낮추든 높이든) 거부하며, 이 값이 저장되거나 적용되지는 않습니다. 배송비는 상품 합계 20,000원 이상 무료, 미만 3,500원입니다(팀 합의 2026-10-26).

## 배송지 검증 (주문 당시 복사 저장 전에 서버가 확인)

화면(zod)과 서버(주문 도메인)가 같은 규칙을 씁니다. 틀리면 422이고 아무것도 저장하지 않습니다.

| 항목      | 규칙                                                                                                                 |
| --------- | -------------------------------------------------------------------------------------------------------------------- |
| 연락처    | `0`으로 시작하는 숫자 9~11자리                                                                                       |
| 우편번호  | 숫자 5자리, 01000~63999 범위, 같은 숫자 반복(11111·00000) 거부. 12345 같은 연속 숫자는 실제 번호일 수 있어 막지 않음 |
| 기본 주소 | 5~200자, 한글 2자 이상 또는 영문 3자 이상이 있어야 함. 숫자만·기호만·한두 글자 반복은 거부                           |
| 상세주소  | 1~100자, 글자나 숫자가 있어야 함. 같은 글자를 4번 이상 반복(1111)하면 거부                                           |

## 비회원 장바구니

- 브라우저의 `HttpOnly`, `SameSite=Lax` 쿠키(`ugly_market_guest_cart`)에 보관합니다. `localStorage`는 쓰지 않습니다.
- 규칙은 서버 장바구니와 같습니다: 수량 1~99, 합쳐서 99를 넘으면 자르지 않고 거부, 판매 중인 상품만 담기. 쿠키 크기 때문에 상품 종류는 50개까지입니다.
- 쿠키는 믿을 수 없는 입력으로 보고, 읽을 때 상품 ID 형식·수량·중복을 다시 검사해 올바른 줄만 남깁니다.
- `/cart`는 비회원에게 열려 있고 `/cart/checkout`과 마이페이지만 로그인이 필요합니다. 비회원에게는 "로그인하고 주문하기"를 보여 줍니다. 찜·쿠폰 탭은 화면에서 로그인을 확인합니다.
- **로그인 후 합치기**: FastAPI 로그인 직후 `/cart`나 `/cart/checkout`에서 비회원 장바구니 전체를 `POST /purchases/cart/merge` 한 번으로 계정 장바구니에 합치고, **성공했을 때만** 쿠키를 지웁니다. 아래 "합치기는 멱등"을 참고하세요.

실제 DB 테스트(`tests/test_cart_db.py`, `tests/test_order_db.py`, 28개)는 실제 계정(`auth.users` + `app_users` 같은 UUID)을 만들어 실제 로그인으로 받은 토큰으로 검증하고, 끝나면 만든 계정·상품·주문을 모두 지웁니다.

- 정상: 담기 → 수량 변경 → 주문 → 목록·상세 재조회, DB에 주문·주문 상품(복사본)·결제 완료 상태 저장, 장바구니 정리
- 거부: 빈 장바구니, 판매 중지 상품, 잘못된 수량, 잘못된 배송지·결제 수단, 화면 금액 조작 → 모두 저장 없이 거부되고 장바구니는 유지
- 권한: 로그아웃한 토큰 401, 비활성 계정 401, 다른 사용자의 장바구니·주문은 404
- 합치기 멱등: 같은 합치기 요청을 5번 반복해도 수량 그대로, 기존 수량이 더 크면 유지·비회원 수량이 더 크면 그 값, 동시 요청 3개도 같은 결과, 판매 종료·없는 상품은 건너뜀, 잘못된 줄이 하나라도 있으면 전체 거부
- 동시성: 같은 `request_key` 동시 요청 3개 → 주문 1건(201 하나, 200 둘), 같은 상품 동시 담기 3개 → 수량 합산, 합쳐서 99 초과는 하나만 성공
- 롤백: 주문 저장 후 장바구니 정리 단계에서 장애를 일으키면 주문·주문 상품이 남지 않고 장바구니 유지, 장애가 풀린 뒤 같은 요청은 정상 처리
- 스냅샷: 주문 뒤 상품 이름·가격이 바뀌어도 주문 상세는 주문 당시 값
- 테스트가 실제로 잘못된 코드를 잡는지 확인하려고 규칙을 일부러 깼습니다(사용자 잠금 제거, 장바구니 미정리, 남의 주문 조회 허용, 전각 숫자 허용 등). 각각 관련 테스트가 실패했습니다. 서비스의 명시적 롤백 호출을 빼도 DB 테스트가 통과했는데, DB 연결을 닫을 때 미커밋 변경이 자동으로 취소되기 때문입니다(보장은 DB 수준에서 지켜집니다).

### 브라우저로 직접 확인 (로컬 프런트 + FastAPI + 팀 DB, 테스트 계정은 확인 후 삭제)

(합치기 방식 변경 뒤 다시 확인) 계정 장바구니에 당근 3개가 있는 상태에서 비회원으로 당근 2개·사과 1개를 담고 로그인 → 결제 화면에 당근 3개(5개가 아님)·사과 1개, DB에도 같은 값. 이전 확인: 비회원 상태에서 상품 2종을 담고 수량을 바꿈 → "로그인하고 주문하기" → 이메일 로그인 → 결제 화면으로 돌아오며 비회원 장바구니가 합쳐지고 기본 배송지가 채워짐 → 주문하기 → 주문 상세(결제 완료, 상품·배송지·금액·결제 수단) → 주문내역에 표시, 헤더 장바구니 0개. DB에도 주문 1건·주문 상품 2건·장바구니 0건으로 저장됐습니다.

### 알게 된 점 (형준 님 확인 요청)

- 팀 DB의 **세션 풀러는 동시 접속이 15개**로 제한됩니다(`EMAXCONNSESSION`). 팀원 서버·테스트와 나눠 쓰므로 동시 요청 테스트가 간헐적으로 실패했습니다. 동시 요청 수를 3개로 줄이고 테스트용 연결은 바로 반환하도록(NullPool) 고쳤으며, 한도가 가득 찬 경우 건너뜁니다.
- `core/database.py`의 엔진은 기본 풀(5 + 초과 10 = 최대 15)이라 서버 하나가 한도를 거의 다 쓸 수 있습니다. `pool_size`·`max_overflow`를 작게 두거나 트랜잭션 풀러를 쓰는 것을 검토해 주세요. 공통 파일이라 이 PR에서는 바꾸지 않았습니다.

- 변경된 곳: 장바구니 담기·수량 변경(`ensure_stock`), 합치기(재고보다 많으면 재고만큼만 합침), 주문 생성(상품 행 쓰기 잠금 + 조건부 차감), 오류 응답(재고 부족 409 + `available`)
- 백엔드 `python -m pytest`(팀 DB 연결): **475 passed**, 건너뜀 2. 프런트 `npm test` **156 passed**, `typecheck`·`lint` 통과
- 브라우저 한 사이클(로컬 프런트 + FastAPI + 팀 DB): 비회원이 흙당근 3개 담기 → 수량을 올리다 재고 20개에서 "재고가 20개 남아 20개까지만 구매할 수 있어요" 안내 → 2개로 줄임 → 로그인 → 합쳐진 장바구니로 결제 화면 → 주문(상품 5,800원 + 배송비 3,500원 = 9,300원, 결제 완료) → 주문 상세. 주문 뒤 장바구니는 비었고 흙당근 재고는 20 → 18로 줄었습니다. 확인 뒤 테스트 계정과 주문을 지우고 재고를 20으로 되돌렸습니다.
- 알게 된 점: 팀원 서버가 동시에 떠 있으면 DB 연결 한도(15개)에 걸려 일부 요청이 간헐적으로 500이 됩니다(`EMAXCONNSESSION`). 로그인 직후 화면이 한 번 "계정 확인이 필요해요"로 보였다가 다시 불러오면 정상이었습니다. 코드 문제가 아니라 연결 한도 때문입니다.
